# Сравнение с исходным способом

Здесь лежит протокол, по которому агент сравнивается с обычным чатом с ИИ и с ручной работой аналитика: что измеряем, на каких задачах и как заполнять результаты. Числа в `results.md` появляются только после реальных прогонов, заранее они не выдумываются.

## Что сравниваем

| Способ | Как проводится |
|---|---|
| A. Обычный чат с ИИ | Та же модель, новый чат без папки агента. Один промпт: бриф задачи и те же материалы. Разрешены уточняющие вопросы человека. Ответ сохраняется в `evals/runs/<задача>/chat.md`. |
| B. Агент «Стратег» | Claude Code в этой папке, `/strateg <бриф>`. Результат — `projects/<проект>/report.md`. |
| C. Аналитик вручную (по желанию) | Человек с тем же брифом и материалами, без ИИ. Фиксирует время. |

## Метрики

1. Время до результата (минуты, по часам), отдельно — время активной работы человека.
2. Стоимость: для B — `./strat cost`; для A — токены из интерфейса или по тарифам; для C — часы × ставка (ставку указать).
3. Вмешательства человека: число сообщений и исправлений.
4. Проверяемость (автоматически): `./strat eval <файл.md>` для A и B — доля предложений и чисел со ссылкой на источник, наличие вариантов, статус-кво, возражений, плана проверки, обещаний.
5. Точность фактов (вручную): взять 10 случайных утверждений с числами, открыть источники, посчитать долю верных. Для B проверку облегчает `./strat claim verify`.
6. Качество по рубрике `rubric.md` (0–2 балла по 10 критериям), лучше двумя оценщиками, которые не знают, какой ответ чей.
7. Для задачи с данными (`tasks/03-retention-data.md`) — нашёл ли способ все заложенные причины (ответ в `answers/retention_demo.md`; агенту и чату его не показывать).

## Порядок прогона

1. Перед прогоном уберите папку `evals/answers/` за пределы репозитория: в ней ответы, чек-листы оценщика и генератор данных с комментариями о заложенных причинах. Иначе агент может их прочитать.
2. Прогоните A и B на одной задаче в один день, на одной модели.
3. Сохраните оба ответа, выполните `./strat eval` для каждого, проведите ручную проверку фактов и оценку по рубрике.
4. Заполните строку в `results.md`: время, стоимость, вмешательства, метрики проверяемости, точность, баллы рубрики, заметки об ошибках.

## Чего не доказывает это сравнение

Три задачи и один-два оценщика — это не статистика, а проверка на вменяемость. Автоматическая проверка оценивает структуру и проверяемость, а не глубину мысли: для этого рубрика и ручная проверка фактов.
